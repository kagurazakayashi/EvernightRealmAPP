# 長夜幻境 Web（EvernightRealm Web）

> EvernightRealm のクライアントインターフェース — ブラウザまたはデスクトップアプリから、仲間だけのプライベートな世界へ。

[English](./README.md) · [简体中文](./README.zh-CN.md) · [繁體中文（台灣）](./README.zh-TW.md) · [日本語](./README.ja-JP.md)

## これは何？

これは長夜幻境（ちょうやげんきょう／EvernightRealm）のクライアントです。自己ホスト型・オフライン優先のプラットフォームで、小規模なプレイヤーグループ向けです。アクティビティ、キャラクター、アセット、チャットがすべてここで動きます — ローカルネットワーク内で完結し、インターネットもクラウドアカウントもテレメトリも不要です。

## 機能（開発中）

- **アクティビティビュー** — シーン、フェーズ、イベントの展開を追う
- **キャラクターパネル** — プレイヤー・NPC・管理者のアイデンティティを一つのプライベートな世界で
- **アセット管理** — 監査可能な所有権を持つ仮想アイテムの閲覧と取引
- **プライベートチャット** — メッセージは自分のサーバーだけに保存
- **オフラインファースト** — クライアントは完全に自分のローカルサーバーと連携し、クラウドに依存しない

## 現在の状況

活発に開発中です。安定版は未リリースです。

## リリース後の利用方法（予定）

- 同じローカルネットワーク内のブラウザでホストのアドレスを開くだけで参加可能。インストール不要
- Windows・macOS・Linux 向けデスクトップアプリも提供予定
- 第三者登録は不要。データはホスト機だけに保存

## 対応言語

簡体中文、繁体中文（台湾）、English、日本語。表示言語は既定ではシステム言語に従い、サーバー入口ページで切り替えると選択が記憶されます。対応外のシステム言語は English に戻ります。

## サーバー接続確認

サーバー入口ページには「サーバー接続確認」があります。あなたのサーバーの稼働確認と時刻の端点を読み取り、サービス名とバージョン、サーバーの UTC 時刻、そのサーバー表示タイムゾーンに変換した現地時刻、そして今回の要求識別子を表示します。確認が失敗した場合は、理由（接続できない、応答がない、サービスが準備できていない等）とエラーコード・要求識別子のみを表示し、成功したように見える数値は画面に残しません。すべての値はサーバー由来で、本機時計やサンプルデータは使いません。

## Root 初期化の案内

新しいサーバーにはまだ Root がありません。入口ページには読み取り専用の「Root 初期化チェック」カードがあり、サーバーに初期化状態を照会して、5 つの結論のうち実際に該当する一つだけを正直に表示します。未初期化、初期化済み、サーバーに接続できない、サーバーが報告を拒否した、今回は確かな答えが得られなかった（アドレスが未保存のときはそう告げ、要求は一切送りません）。サーバーが「まだ Root が無い」と答えた場合のみ、サーバーが常駐するマシンで行う手順（サービスを停止、新しいデータディレクトリならまず構造を作成、`evernight-server init-root --password-stdin` を実行、サービスを再起動、この画面でもう一度照会）を列挙します。照会が失敗した状態を何かの状態として言い張ることはなく、「初期化を確認」は単にもう一度尋ねるだけです。すべての要求は読み取り専用で、認証情報を作成・変更・上書きしません。

このカードはパスワードを収集しません。カード内にパスワード入力欄は無く、認証情報をサーバーへ送る事もありません。Root の初期化はサーバー本体でのコマンド実行だけが経路です。認証情報が存在する段階になるとカードは手順を列挙せず、初期化済みであるとだけ伝えます。ログインの入口は下の「ログインとセッション」カードに移っており、このカード自体は読み取り専用のままとします。

## ログインと身分の復元

サーバーの初期化が終わると、入口ページの「ログインとセッション」カードがアプリへの入り口になります。

- ログインページはまず、今回ログインするサーバー（有効なアドレス、探索済みならサービス名とバージョンも）を表示し、そのうえで認証情報を求めます。経路は二つ：Root ログイン（パスワードのみ）とアカウント ログイン（ログイン名とパスワード）。アカウント側は既存のサーバー API を再利用します。アカウントが生まれる入口は三つだけです。Root が Root コンソールで管理者を作成する場合、サーバーのアカウント作成ポリシーが経路を開けている間に管理者が管理者コンソールで通常アカウントを作成する場合、そしてポリシーが開放しているときのセルフ登録画面からの匿名送信です。最後の経路は誰も自動的にサインインさせません。招待コードによる登録を含む三つのモードがすべて提供されています（登録画面はサーバーの `invite_code_required` を読み、招待コードモードのときだけ招待コード欄を出し、そのコードを同じ `POST /auth/register` に渡して一点利用で一般アカウントに交換させます）。ゲスト入室は現在提供されています。それも制限された経路のままです。サーバー入口層に独立したカードがあり、サーバーの `guest_open` を読みます。この臨時身分が作られるのは、そのカード自身のボタンを押したときだけで、ページの読み込み・更新・再接続では何も書き込みません。
- 失敗は種類ごとに正直な一言ずつ：資格情報の拒否は単一の文言（サーバーは「アカウント無し」と「パスワード不一致」を区別せず、画面も分けられない）、速率制限は後で再試行、接続不能と端末側の保存失敗はそれぞれの言葉を返します。どの表示も入力されたパスワードを再利用せず、サーバー本文をそのまま見せることもありません。パスワードはこの端末に保存されず、自動入力もされません。
- ログイン成功後の身分はサーバーの回答が基準で、フォームの選択ではありません。保護ページは必ずセッション確認を通過し、サーバーが答えるまで保護された内容は一文字も描画されません。ログインページへ戻された際に保持される「戻り先」は本アプリに登録された正当なルートのみで、それ以外（外部 URL を含む）はすべて入口ページに戻ります。
- アプリを開き直すと前回のセッションの復元と検証から始まります。検証中は中立的な案内だけを表示し、有効なら主体・デバイス識別子・失効時刻（UTC）を、サーバーが確認した事実としてカードに列挙します。無効と判定されたらログインへ戻り、端末に保存されたセッション資格情報を削除します。
- ログイン済み状態の「ログインとセッション」カードにはログアウトボタンがあります。サーバーに対してこのセッションの失効を要求し、Web 経路では同名・同属性の Cookie 削除指令を受け取り、ネイティブ経路ではこのサーバー用のシステム級安全ストレージの情報を消します。もう一度ログアウトしても冪等で、新しいセッションは作られず「再ログイン」も促されません。サーバーに届かない場合は端末側だけ確かに消したうえで、「ローカルは消したがサーバー側の失効は未確認」と分けて伝え、「すべてのデバイスがオフラインになった」とは言いません。
- サインイン済みのカードには「自分のデバイス」の入口もあります。サーバーの回答どおりに自分のセッションを一覧し、いま使っているデバイスを印で示し、別のデバイスを取り消せます。範囲はサーバーが自分の主体内に限定するため、ほかのアカウントのデバイスを名指しすることはできません。現在のデバイスを取り消すのは、そのデバイスでサインアウトするのと同じです。一覧が古い・すでに無効・サーバーに届かない、の三つはそれぞれそのまま伝え、起きなかった取り消しを成功として報告しません。
- サインイン済みのカードにはパスワード変更の入口もあります。変更にはリクエスト内で現在のパスワードをその場で差し出す再認証が必要で、「まだサインインしている」ことは変更の承認にはなりません。変更が成功するとサーバーの方針どおり自分名の全セッション（この端末を含む）が失効し、アプリはサインアウト状態に移って新しいパスワードでの再サインインを促します。パスワードはいかなるローカルキャッシュにも残りません：3つの入力欄はダイアログ内にのみ存在し、使い済み即消去、すべて伏字です。「初回サインイン時にパスワード変更必須」の印が付いたアカウントに対し、サーバーは変更・ログアウト・現在のセッション照会だけを通し、他の保護機能は専用マシンコード 2010 を返します。カードはその2つの入口だけを示し、必ず拒否されるボタンは出しません。
- セルフ登録画面は外の人のための扉です。エントリーページに出るのは、サーバーの匿名能力（`sign_up_open`）がこの経路が開いていると答えたときだけでした。基本の入力三項目——ログイン名・表示名・本人が選ぶパスワード——に加え、サーバーの三つ目の真偽値（`invite_code_required`）が招待コードモードのときだけ出す招待コード欄があります。招待コードは一時的な秘密で、一つの入力欄に打つだけでこのリクエストの本体でのみ送信され、アドレスバー・ブラウザの履歴・ログ・どのキャッシュにも残らず、成功時は他の欄といっしょに消えます。役割やアカウント種別や承認状態を選ぶ操作はこの画面のどこにもありません。生まれる主体の種別はエンドポイントが決めるものであり、そういう項目を载せた要求は書き込みの前にサーバーが拒否します。扉を示すことは准入の保証ではありません。サーバーは書き込みのトランザクション内で方針を読み直すので、Root が途中で戻したスイッチを古い画面で通り抜けることはできません。
- 送信の後に何が残るかはその瞬間のモードで決まり、画面は受け取った答えを伝えるだけです。`open` では、選んだばかりのパスワードですぐサインインできるアカウントが生まれ、要約もそう書きます。`approval` では同じ三項目が申請として受け付けられます。アカウントは存在し、ログイン名は占有され、パスワードは保存されています——しかし誰かが承認するまでサインインはできません。画面はそこに「申請は送信済み、まだ承認されていません」と正直に書き、失敗すると分かっているログインの短縮ルートは置きません。`invite` では有効なコードがアカウント作成と同じトランザクション内で利用され、選んだばかりのパスワードですぐサインインできる一般アカウントが生まれます——ログインの挙動が同じなので要約は公開モードとまったく同じ読み味になります。アカウントを作れないコード（記入漏れ、形式不正、失効、期限切れ、使い切り、または併発で先に使われた）は詳細を漏らさない 2023 の一文で拒否され、どれに該当するかはわざと示しません。匿名の能力答えは意図的にモード名を明かさないので、これは画面の推測ではなくサーバーの書き込みが答えます。
- 申請者自身は別の画面で自分の状況を知ることができますが、それはログインではありません。照会のたびに認証情報を確認し（ログイン名とパスワードは POST 本体に置き、URL には入れません）、結果（待機中・承認済み・却下）、提出日時、そして決定がある場合は決定時刻だけを返します。セッションは発行せず何も保存しません。Cookie もトークンも残らず、更新や离开で再利用できるものは残りません。待ち位置も審査者も理由文もありません——それはサーバー側の事情です。承認済みと分かった人は通常のサインイン画面へ導かれます。この経路がアカウントを早めに使えるようにすることはありません。
- 同じログイン名での再提出は誰でも同じ一意性の答えに当たります。申請は名前を占有し続け、却下された申請も同じです。ですから却下された人は同じ名前でもう一度できず、他の人もその名前を得られません。その後サーバーのモードを切り替えても、提出済みの申請は一つも変わりません。方針のスイッチは誰も通過させず、履歴も捨てません。必要なのは明示的な決定で、その決定は管理者コンソールの登録申請画面で下されます。

- サーバー入口層にはゲストの扉としてのカードがもう一枚あります。サーバーの匿名応答 `guest_open` がこの道を開けているときだけ現れます。登録画面と違って（登録は誰もサインインさせません）、このカードのボタンを押すと臨時身分が作られると同時にセッションが渡されます。`POST /auth/guest` の Cookie はサインインと同じ配布経路を通るので、ブラウザは HttpOnly Cookie に任せ、ネイティブはプラットフォームの安全保存領域に書き込みます。ニックネーム欄は任意で、表示情報にすぎません——空欄のままならサーバー自身が仮の番号を付けることも、送信する前に書かれています。カードは自分自身の制限も先に述べます。この身分はどの活動にも属さず、サーバーレベルの授権を持たず（管理系と Root 系の画面は 2011 を返します）、変更すべきパスワードもありません——だからこそサインイン済みのカードはゲストに「パスワード変更」のボタンを出さず、本当に使える端末管理・ローテーション・ログアウトだけを並べます——そしてセッションの有効期限切れ、自前のログアウト、端末の切り替え、本機の認証情報を消した時点で、この回は終わりです。「ニックネームで取り戻す」画面は意図的に存在しません。打ち込める名前は認証情報ではなく、このアカウントをどうするかは、管理者が通常アカウントカタログで本人を確認したうえで決めます。ページの読み込み・更新・再接続・失敗した再確認では何も作成されません——作成するのはあのボタンだけで、処理中の連点も一回の送信にとどまります。入室後に着くのはプレイヤー面で、そこには「この身分はまだどの活動にも属さない」と正直に書かれます。身分の行はサーバー自身の `account_type` を読み、「ゲスト（一時的な身分）」と表示されるので、更新しても再起動しても発言は事実と合います。

- Root コンソールに今日配線済み機能は八つあります：サーバー管理者の作成、管理者カタログの閲覧、単一記録の表示と編集、管理者のログイン停止と再開、管理者ログイン認証情報のリセット、管理者のソフト削除、サーバーのアカウント作成ポリシー、そしてサーバー登録招待コードの管理です。八つ目のこのカードは Root が発行した招待コードをページ区切りで並べ、状態（有効／期限切れ／使い切り／失効済み）とラベルで絞り込めます。各行はメタデータだけを示します——ラベル、派生した状態、利用回数と上限、発行・期限・（失効済みのときは）失効時刻——コードそのものは決して出しません。発行は確認ダイアログを経てから、選択可能な一度限りの表示欄に完全な招待コードを出します。画面は自動コピーも共有ボタンも QR コードも持たないので、失くしたら読み戻すのではなく新しく発行し直すしかありません（サーバーはハッシュしか保存しません）。失効はそのコードを名指しし、以降の利用だけを遮り、一方向で、削除ではないと伝えます。繰り返し失効は 2022 を返し、再読み込みの出口しか出しません。このカードは証明書の管理（発行・一覧・失効）のみを行い、自分でコードを利用することはありません——利用は登録画面側の仕事で、外の人が自分のコードを `POST /auth/register` に持ってきます。方針を invite に切り替えるのは別の戦略カードの別個の決定です。この役割分担は意図的なもので、経路が欠けているわけではありません——ここで Root が発行したコードは、方針を invite に設定すれば登録画面で利用できます。。作成フォームが渡すのは三つの値——ログイン名、表示名、一回限りの初期パスワード——で、役割や主体種別の項目は存在しません。「管理者を作成する」ことを決めるのはエンドポイントそのものだからです。初期パスワードは表示し返さず、ローカルのキャッシュにも残さず、画面のどこにも現れません。新しいアカウントは初回サインインでそれを必ず変更しなければならず、変更し終えるまでサーバー側が他の保護された機能をすべて専用マシンコード 2010 で拒否します。認証情報のリセットも同じ作り方です。Root が伏せ字の入力欄に置き換えパスワードを打ち、送信すると欄はただちに空になり、画面がパスワードを読み返すことはなく、確認ダイアログがリクエストを出す前に今回のリセットで何が起こるかを読み合わせます。カタログは固定長の簡易一覧ではなく本物のページ表示です。ページ送りと総件数はサーバーが返し、絞り込みは状態の一種だけ（削除済みのアカウントも並びます）、授与の時刻が新しい順に並び、設定上の Root が編集可能な行として並ばないことは設計として明言します。行を開くと、その単一記録をサーバーから読み直してから編集フォームを表示します。フォームが編集できるのは表示名だけで、見た現在の値と共に送信されるため、古い画面に対する保存は 2013 で拒否され、何も上書きしません。停止は確認ダイアログが必須で、対象を名指しし、影響（新規ログイン拒否と配下の既存セッション全部の取消）と起こらないこと——これは削除ではない——を一度に読み合わせます。再開が回復するのは新規ログインの能力だけで、停止時に取消されたセッションは復活せず、未完了の初回パスワード変更の要求も有効なままです。削除はそれ自体が終端の状態であり、専用の確認ダイアログを通ります。アカウントを名指しし、送信する前に結果を読み合わせます。ログインが止まり、既存セッションは取り消され、再開の入口はありません。停止と削除は別の状態なので、再開の操作が削除済みアカウントを復活させることはなく、そのようなボタンを画面は用意しません。削除済みの記録は読み取り専用になります。サーバーが書き換えた仮の表示名と削除時刻を表示し、過去の操作の身元は今も解決できることを説明します。授与もセッションも監査も同じアカウントを指し続けるからです。設定上の Root 認証情報はカタログの行ではないため、削除の対象にはなり得ません。「Root を停止」「管理者が同格を停止」を送信する経路はこの画面に存在しません。根拠が古い状態変更や重複操作は 2014 で拒否され、画面は「読み直して確認」を導き、ボタンを再押下させることはありません。削除済みのアカウントに対する編集・認証情報のリセット・二度目の削除は 2015 で拒否され、結果が不明な削除を自動で送り直すこともありません。画面に出る数字もラベルもすべてサーバー応答由来で、楽観的な埋め合わせはしません。七つ目はポリシーカードです。3 つの値（管理者が通常アカウントを作成できるか、セルフ登録モード、ゲストアカウントを作成できるか）をサーバーから読み直し、保存前に必ず確認ダイアログを通ります。画面は二つのことを分けて言います。保存するのはこの構成の意向であり、「管理者による通常アカウント作成」、セルフ登録、招待コード、ゲスト入室の四つの経路はどれも今は動いているので、各行はそのままスイッチに従い、裏の実装がなくて常に閉じる行はもう残っていません。モードは closed・open・approval・invite の四つを選べます。approval が受け取るのは承認までにサインインできない申請で、承認の意味もこのカードはそのまま書きます。判定は管理者コンソールの登録申請画面で行われ、そこでの決定がサーバーレベルの役割を与えることはありません。invite は有効なコードを持つ人だけが自分で登録できるモードで、カードはそれも正直に伝えます——コードはアカウントごとに一点利用され、サーバー役割を一切与えず、作られるのは公開モードと同じく直ちにログインできる一般アカウントです。まだこのカードが出せないモード（将来増えた名前）はサーバーの原文のまま表示してこっそり書き換えたりしませんが、ここに出す選択肢はサーバーが実際に受け取るものと同期させる必要があります。書けるモードを一つでも欠けば、他の二項目を保存するたびにサーバーが記録したモードを打ち消すことになるからです。読めないときカードは推測値を一切表示せず、書き込みが失敗すると 3 つの値は直前のサーバー側の真実に戻り、結果が不明な保存を送り直すこともありません。
- 管理者コンソールは本日6項目の機能を備えています：通常アカウントの作成、通常アカウントカタログの参照、単一レコードの基本資料の読み取りと維持、通常アカウントのログイン停止と再開、通常アカウントのログイン認証情報のリセット、そして登録申請の承認または却下。フォームは三つの値を渡します。ログイン名、表示名、使い捨ての初期パスワードで、役割・アカウント種別・活動用の欄はありません。通常アカウントかどうかはエンドポイント自身が定めるため、サーバーレベルの授与も活動プロフィールも資産も付きません。スイッチの状態は予読しません。サーバーは作成トランザクション内でポリシーの現在値を読み直し、閉じていれば機械コード 2017 を返し（2011 の「権限なし」とは別の一文で、Root がこのエンドポイントを通っても同じく拒否されます）、名前が埋まっていれば 2012 を返し、成功カードには「アカウントは作成済みだが、まだどの活動にも属していません」と明記します。初期パスワードは再表示されず、どの状態にも保存されず、画面のどこにも現れません。新しいアカウントは初回サインイン時にパスワードを変更する必要があり、他のすべてのアカウントと同じサーバー側の閘門（2010）に縛られます。
- 通常アカウントカタログは本日、参照と維持ができます。ページ区切りのカタログは状態（すべて／有効／停止済み）、出所（すべて／通常アカウント／ゲストアカウント）、名称キーワード（ログイン名と表示名の二欄に対して部分一致）で絞り込め、ページ番号と総数はすべてサーバー側のエコーをそのまま使います。行を開くと、その識別子で単一レコードをサーバーから読み直してから編集フォームが表示されます。このカタログに管理者は並びません。Root も並びません。サーバーレベルの授与を持つ人は Root の管理者カタログに属し、二つのカタログは互いに排他です。管理権限のないセッションが読むと空一覧ではなく「権限がありません」（2011）を受け取り、匿名は 2002 です。フォームは表示名だけを変更し、見ている現在の値とともに送信します。古くなった画面に対する保存は拒否され（2013）何も上書きしません。画面は「この資料を再読み込み」を提示し、保存ボタンをもう一度押すことは勧めません。ログイン名はここで変更できず、認証情報・権限・安全状態もこのフォームにはありません（本体に他の項目を足せばサーバーが 1004 で拒否します）。単一レコードに活動・資産・メッセージの三欄はありません。それらのモジュールは未実装であり、空一覧や 0 で調べられる事実を装うことはしません。識別子の形が不正、アカウントが存在しない、その人は管理者、すでに削除済み、という四つの入力はすべて同じ 1001 を返すので、このエンドポイントは「あの人が管理者かどうか」の探針にはなりません。
- 通常アカウントのログイン停止と再開は同じ単一レコードのカードに配線済みで、画面はまず範囲を言い切ります。ここで動すのはこのアカウントがサーバー全体で持つログイン能力であり、ある活動の中だけのプレイヤー制限ではありません。停止すれば今後のログインは拒否され、その人が各デバイスで今持つセッションはすべて取り消されます。送信前に確認ダイアログを必ず通し、対象を名指しして影響範囲と「これは削除ではない」を読み合わせ、キャンセルならリクエストを一つも送りません。どのボタンを出すかはサーバーが読み返した現在の状態だけが決めます（有効なら停止のみ、停止済みなら再開のみ、認識できない値には方向を推測せず一文だけ）。根拠にする値も前回サーバーから読んだ状態なので、古くなった画面に対する送信は 2014 で拒否され何も起こらず、画面は「この資料を再読み込み」を促して同じボタンをもう一度押させません。成功後は状態、停止時刻、「今回何件のセッションが終了したか」をすべてサーバーの応答に置き換え、カタログも読み直します。再開が戻すのは再度ログインできる能力だけで、停止中に取り消されたセッションは復活せず、未完了の初回パスワード変更は引き続き 2010 に阻まれ、削除済みのアカウントをこれで復活させることはできません。訪問者アカウントも同じ一組の操作を通ります。このカタログの定義は「サーバーレベルの授与を一切持たない」だからです。活動内の発言禁止・取引凍結・陣営制限はここになく、使えるふりもしていません。
- 通常アカウントの認証情報リセットは同じ単一レコードのカードに三番目のホワイトリストとして配線済みです。`PUT /admin/accounts/{account_id}/password` の本体は `password` の 1 項目だけで、依拠値は意図的にありません。実行者に「現行のハッシュ」といった誠実な錨はあり得ず、結果が不明なときにそのボタンを押し直すのは再試行ではなく 2 回目の完全なリセット（その間に発行されたかもしれないセッションをもう一巡取消し、監査をもう 1 件残す）だからです。画面は自動再送しません。受け渡しは Root 側で承認済みの方式沿用です。パスワードは管理者が自分で渡し、サーバーは生成せず、エコーせず、既定パスワードも置きません。入力欄は伏せられ、リクエスト送信前に空になり、成功の一文は「今回何件のセッションを終了させたか」と「線下で手渡し、初回ログイン時に変更が必須」だけを伝えます。その文字列はその後どこにも表示されず、ログ・監査・閲覧可能な設定・自動コピーのクリップボードにも入りません。停止中の対象もそのままリセットできます（リセットは停止解除ではないため、画面は状態で分岐しません）。リセットは停止・削除の終態・果たしていない初回変更の義務に手をつけません。今日アカウント単位の承認状態は無いので「承認待ち」は正直に「初回変更を果たしていない」であり、リセットが書くのは「変更しなければならない」で「変更しなくてよい」ではありません。ゲストアカウントはこの経路の対象外です。彼には一般的なパスワードが無く、代わりに書き込めば通常アカウントへの昇格と同じになり、それは今後来るゲスト昇格の機能が決めます。画面はゲストにボタンを置かずこの一文だけを添え、サーバーも同じ答えを本ステップ唯一の機械コード 2018 で返します。権限不足（2011）、対象がこの台帳に居ない（1001）、パスワードがサーバーの規則に通らない（1004）はそれぞれ別の一文で、画面の数字と状態はすべてサーバーの応答から来ています。
- 登録申請は管理者コンソールに専用の画面を持ちます。`GET /admin/registrations` は審査中と却下済みのものを列挙し、各行はログイン名・表示名・状態・提出日時、そして決定があれば決定時刻だけを示します。これが審査に必要事実の全体で、認証情報もセッション材料も役割欄もありません。通常アカウントカタログは範囲条件の違う別の一冊のままです。2つのボタンはサーバーが返した状態が本当に `pending` のときだけ出ます。却下済みの行には代わりに正直な一文を置きます。ここでの判定は一方向で、開き直す経路はなく、そのログイン名の占有も続くからです。どちらのボタンにも理由の入力欄がありません。内部メモも公開理由も保存されない以上、入力すれば黙って捨てられる欄を置くほうが悪いです。確認ダイアログは対象を名前で示し、何が生じ（自分で選んだパスワードでサインインできる、サーバー役割を一切持たない通常アカウント）何が起こらないか（本人へのセッション発行も、停止の解除も、名称変更も削除もありません）を言い切ります。成功文は PUT 応答から取り、どの決定がどれについて落ちたのかを示します。そのうえで一覧行をローカルで書き換えず再読込みします。承認済みの人はもうこの名簿にいないからです。2021 は「すでに判定済み」の意で、画面は再読込みの出口だけを与え、結果が不明な決定を送り直すことはありません。1001 は対象がこの名簿に無いこと、2011 はこのセッションが誰も判定できないことを意味し、三つの処置はそれぞれ別の一文です。この画面は通知を行いません。このサーバーに通知モジュールは無いため、申請者は自分の認証情報を示し直して状態照会画面で結末を知るだけです。

- Root 管理モジュールの残り部分は開発中です：ログイン済みの主页は真の身分と実際に使える入口だけを示し、示例データで取り繕いません。身分の行はサーバーが返す `roles` に従うため、管理者には「サーバー管理者」と表示され、授与を持たないアカウントには出ません。管理者自身が同じフォームを開いても、「権限がありません」の一文（マシンコード 2011）が返るだけで、サインインし直しても使えるようにはなりません。ネイティブクライアントのセッション資格情報は OS レベルの安全ストレージに、Web では HttpOnly Cookie に管理され、平文でディスクに置かれることはありません。Web ではその Cookie に Secure が付くのは、ページが実際に HTTPS で配信されているときだけです。平文 HTTP の LAN 配置では、ブラウザ側の防御は SameSite とサーバーのオリジン判定が担うため、HTTPS を使うには自分で TLS 終端のリバースプロキシをサーバーの前に置く必要があります。

## サーバーアドレス

サーバー入口の画面から使用するサーバーのアドレスを入力し、この端末に保存できます。テストサーバーの切り替えに再ビルドは不要です。受け付けるのは認証情報を含まない完全な `http://` または `https://` のアドレスだけで、応答が確認できたアドレスのみ保存します。形式が不正な場合は具体的な理由を表示し、リクエストは一切発出しません（例：「アドレスは http:// または https:// で始めてください」）。形式は正しいが接続できない場合は保存せず、成功したふりをして理由を隠すこともありません。使用中のアドレスとこの端末に保存済みのアドレスは分けて表示し、現在使われている値の出所も示します。デバッグビルドではビルド引数 `--dart-define=ER_SERVER_BASE_URL` が優先され、その場合は端末に保存したアドレスがまだ有効でないことを画面に明示します。入力内容は自分の端末にのみ保存されます。

## 画面で問題が起きたとき

アプリのある部分を表示できない場合、画面は安全な案内表示に切り替わります。問題が起きた場所（画面の描画、バックグラウンド処理、サーバーとのやり取り）を説明し、本機のログと突き合わせるための診断コード、および要求に関わる場合はサーバーの要求識別子を表示します。「利用可能なページに戻る」を押すと使える画面に戻れます。案内表示はエラー原文・スタックトレース・サーバーアドレスを示さず、内容を外部に送ることもありません。問題は本機のみに記録されます。

正直にお伝えすると、ちょうど失敗した部分は戻った後しばらく空白のままになり、画面が再構築されるまで戻らないことがあります。同じ問題が繰り返される場合は、案内表示がアプリの再読み込みを促します。

## ソースからのビルド

各プラットフォームのアイコンと起動画面は生成されるもので、バージョン管理には含まれません。`assets/icons/` の 4 つの元画像から生成されます。クローン直後はビルドの前に

    python tools/icons/generate_icons.py

を実行してください。アイコン資源が無いと Android / iOS / macOS / Windows のビルドは失敗し、Web ビルドはアイコン無しで出力されます。`python tools/icons/generate_icons.py --check` は現状を照合するだけで、何も書き込みません。詳細は `tools/icons/README.md`。
