# 長夜幻境 Web（EvernightRealm Web）

> 長夜幻境的客戶端介面——用瀏覽器或桌面客戶端，走進屬於你小圈子的私密世界。

[English](./README.md) · [簡體中文](./README.zh-CN.md) · [繁體中文（臺灣）](./README.zh-TW.md) · [日本語](./README.ja-JP.md)

## 這是什麼？

這是長夜幻境的客戶端。長夜幻境是一個自主部署、離線優先的平臺，面向小規模玩家群體。活動、角色、資產與聊天都在這裡呈現——全部在區域網內完成，不需要公網、雲賬號或遙測。

## 功能規劃（開發中）

- **活動檢視**：跟隨場景、階段與事件的發展
- **角色面板**：玩家、NPC 與管理員的身份，共處一個私密世界
- **資產管理**：檢視與交易虛擬物品，歸屬可審計
- **私密聊天**：訊息只留在你自己的伺服器上
- **離線優先**：客戶端完全對接你的本地伺服器，不依賴雲服務

## 當前狀態

正在積極開發中，尚未釋出穩定版本。

## 釋出後的使用方式（規劃）

- 在同一區域網內用瀏覽器開啟主機地址即可加入，無需安裝
- 也將提供 Windows、macOS、Linux 桌面客戶端
- 無需第三方註冊；資料只儲存在主機上

## 介面語言

簡體中文、繁體中文（臺灣）、English、日本語。介面語言預設跟隨系統語言，可在伺服器入口頁切換並記住選擇；系統語言不在支援清單時回退 English。

## 伺服器連通性檢查

伺服器入口頁提供「伺服器連通性檢查」：向你的伺服器讀取健康與時間端點，顯示服務名稱與版本、伺服器的 UTC 時間、依伺服器顯示時區換算後的當地時間，以及本次請求的識別碼。檢查失敗時介面只說明失敗原因（無法連線、沒有回應、服務尚未就緒等）並給出錯誤代碼與請求識別碼，不會留下任何看起來像成功的資料；所有數值都來自伺服器，不使用本機時鐘或範例資料。

## Root 初始化引導

全新的伺服器還沒有 Root，入口頁因此有一張唯讀的「Root 初始化檢查」卡片：它向伺服器查詢初始化狀態，並如實顯示五種結論之一——尚未初始化、已完成初始化、連不上伺服器、伺服器拒絕回報、這一次的結果不明確（還沒儲存位址時則先說明沒有位址，不發出任何請求）。只有伺服器明確回答「還沒有 Root」時，卡片才列出接下來要在伺服器那台機器上做的事：停止服務、必要時先建立結構、執行 `evernight-server init-root --password-stdin`、重新啟動服務、回到本頁再查一次。查詢失敗不會被說成任何一種狀態；「重新檢查」只是再問一次，全部是唯讀請求，不會建立、更換或覆蓋任何憑證。

這張卡片不收集口令：卡內沒有任何密碼輸入欄，也不把任何憑證發往伺服器——初始化 Root 只有在伺服器本機上執行命令這一條路。設定檔裡已有憑證之後，卡片不再列出步驟，只說明初始化已完成；登入入口就在下方「登入與會話」卡片裡，本卡自身依舊唯讀，不收集任何口令。

## 登入與身分恢復

伺服器完成初始化後，入口頁的「登入與會話」卡片就是進入應用的通道：

- 登入頁先顯示這次要登入的是哪一台伺服器（生效位址，若探測過還帶服務名與版本），再讓你交憑據。兩條通路：Root 登入（只有口令）與帳戶登入（登入名加口令）；帳戶通路復用伺服器既有的登入介面。帳號只從三個入口產生：Root 在 Root 控制台開設管理員，管理員在管理員端建立一般帳戶（以伺服器的帳戶建立策略開放那條通路為前提），以及策略開放時自助註冊畫面上匿名提交的那一個——它本身從不替任何人登入。自助註冊現在三種模式都已上線：開放、審批、以及邀請碼模式（註冊畫面讀伺服器的 `invite_code_required`，只在邀請碼模式下顯出邀請碼欄位，再把碼交給同一條 `POST /auth/register`，由它核銷成一個普通帳戶）。訪客進入現在提供了，而且就是它被限制的那條路：伺服器入口層有一張獨立的卡讀伺服器的 `guest_open`，而只有按下它那顆按鈕才會建立這個臨時身分——頁面載入、重新整理與重連都不寫任何東西。
- 每種失敗各說自己那一句：口令被拒是統一的一句（伺服器不區分「查無此人」與「口令不對」，介面也無從分開）、被限流說稍後再試、連不上和本機儲存失敗各歸各。任何提示都不會回顯你輸入的口令，也不轉述伺服器原文；口令不保存在本機，也不自動填入。
- 登入成功後的身分以伺服器的回答為準，不是表單上選了什麼；受保護頁面一律先過會話檢查，伺服器回答之前不會閃現任何受保護內容。被退回登入頁時保住的「返回目標」只認本應用已登記的合法路徑，其他目標（包括外部網址）一律回到入口頁。
- 應用重開時會先恢復並驗證上一次會話：驗證中只給中性提示；仍有效就在會話卡列出經伺服器確認的主體、裝置識別與到期時間（UTC）；已被判定失效就退回登入並清除本機儲存的會話憑據。
- 已登入態的「登入與會話」卡片上有「登出」按鈕：讓伺服器撤銷這一次綁定的會話——瀏覽器路徑收到同名同屬性的 Cookie 刪除指令、原生路徑清掉這台伺服器在系統級安全儲存裡的那份憑據；重複按登出是冪等的，不會產生新會話也不叫使用者重新登入。連不上時本機照清，提示把「本機已清理」與「伺服器撤銷未確認」分開講，不會謊稱已在伺服器登出，也不暗示所有設備已下線。
- 已登入態的卡片上另有「我的裝置」入口：依伺服器回答列出你自己的會話、標出你正在用的這一臺，並可撤銷另一臺。範圍由服務端限定在你自己的主體內，面板無法指名別人的裝置；撤銷當前這一臺等同於在它上面登出。清單已過期、會話早已失效、連不上伺服器三種情況各說各的，沒發生的撤銷不會被說成成功。
- 已登入態的卡片上另有「變更密碼」入口：改密要求在請求中當場交出現行口令作再認證——「仍處於登入態」從來不是改密的授權；改密成功依伺服器策略讓名下全部會話（含這一臺）退出，界面進入退出態並提示以新口令重新登入。口令不落地任何本地快取：三個輸入欄只存在於對話框中、用完即清且全部遮罩。帶有「首次登入必須改密」旗標的帳戶，服務端只放行改密、登出與當前會話查詢，其餘受保護功能一律回專用機器碼 2010；卡片據此只留這兩個入口，不呈現注定被拒的按鈕。
- 自助註冊畫面是給還站在門外的人的。它只在伺服器的匿名入口能力（`sign_up_open`）說這條路開著時才出現在入口頁，而且收登入名、顯示名與本人自選的口令三個欄位，外加一個只由伺服器第三個布林（`invite_code_required`）在邀請碼模式下才顯出的邀請碼欄位；邀請碼是短暫停留的祕密，只填在一個輸入框、只隨這一次請求本體發送，不進位址列、瀏覽器歷史、日誌或任何快取，成功時連同其餘欄位一起清空。整個畫面上沒有任何角色、帳戶類型或審批狀態的控制項：建出來的是哪一類主體由端點決定，不由表單決定，多帶這類欄位的請求在寫庫之前就被伺服器拒掉。露出這扇門從來不是准入的保證：伺服器在自己那筆寫入交易裡重讀策略，所以 Root 中途翻回去的開關沒辦法靠一張舊畫面走過去。
- 提交之後剩下什麼，取決於伺服器跑的是哪種模式，而畫面只轉述它拿到的回答。`open` 時得到一個立刻能用剛選的口令登入的帳戶，摘要就這麼說。`approval` 時同樣三個欄位交出的是一份申請：帳戶存在、登入名被佔用、口令已儲存——但在有人批准之前它不能登入。畫面這時如實寫「申請已提交，尚未獲准登入」，也不擺一個它知道必然失敗的登入出口。`invite` 時一枚有效碼在建號同一筆交易內核銷，落成一個立刻能用剛選口令登入的普通帳戶——摘要與開放模式讀起來一模一樣，因為登入行為本就相同；換不出帳戶的碼（缺、形狀不合、已撤銷、已過期、用盡、或併發下被搶先用掉）以一句不洩露細節的 2023 拒絕，刻意不說差的是哪一半。匿名入口刻意一直不說模式名字，所以這件事由伺服器的寫入回答，不由介面猜。
- 申請人可以在另一個畫面上問自己的申請怎麼樣了，而那並不是一次登入。它每次查詢都重新驗證憑據（登入名與口令放在 POST 本體裡，絕不進 URL），只回答結局——還在等、已批准、已拒絕——加上提交時刻，以及已有決定時的決定時刻。它不簽發會話、也不儲存任何東西：不下 Cookie、不留令牌，重新整理或離開都不會剩下可被複用的東西；沒有排隊位次、沒有審核人、沒有理由文字，那些屬於伺服器自己的事。在這裡查到已批准的人會被導向一般登入頁；這條通路不會讓任何帳戶提早可用。
- 用同一個登入名重複提交會與其他人的回答相同——申請會繼續佔用那個名字，被拒絕的申請也一樣。所以被拒絕的人不能拿同一個名字再來一次，別人也拿不走。之後切換伺服器的模式不會改變已經交上來的任何一份申請：策略開關既不替誰放行，也不丟任何一份歷史；那需要一個明確的決定，而決定是在管理員端的註冊申請畫面上做出的。

- 伺服器入口層另有一張卡是訪客那扇門。它只在伺服器的匿名 `guest_open` 說這條路開著時才出現；而與註冊畫面不同（註冊從不替任何人登入），按下這張卡那顆按鈕會同時建立這個臨時身分並交回一枚會話：`POST /auth/guest` 的 Cookie 與登入走同一條分發通路，所以瀏覽器把它交給 HttpOnly Cookie 代管，原生端寫入平台的安全儲存。暱稱欄是可選的，而且只是展示資訊——留空時由伺服器給出它自己的臨時編號，這件事在送出之前就先講清楚。這張卡也把自己的限制寫在前面：這個身分不屬於任何活動，不攜帶任何伺服器級授予（管理端與 Root 端對他回 2011），也沒有口令可改——所以已登入的卡片對訪客不擺「變更密碼」那一顆，只給裝置管理、輪換與登出這些真的能用的入口——而會話到期、主動登出、換裝置或清掉本機憑據之後，這一趟就結束了。這裡刻意沒有「憑暱稱找回」那一屏：一個你打得出來的名字不是憑據，這個帳戶之後怎麼處理，是管理員在一般帳戶目錄裡核實這個人之後由他決定。頁面載入、重新整理、重連與一次失敗的重新檢查都不會建立任何東西——只有那一顆按鈕會，而它在進行中連點只發一趟請求。進去之後落到玩家面，那裡如實寫著這個身分還不屬於任何活動；而身分那一行讀的是伺服器自己的 `account_type`，顯示成「訪客（臨時身分）」，所以重新整理或重開之後說的話仍然對得上。

- Root 控制台今天接通了八項能力：開設伺服器管理員、瀏覽管理員目錄、檢視與編輯單筆資料、停用與恢復管理員登入、重設管理員登入憑據、軟刪除管理員、伺服器的帳戶建立策略，以及管理伺服器註冊邀請碼。第八項這張卡分頁列出 Root 簽發的邀請碼，可按狀態（有效／已過期／已用滿／已撤銷）與標籤篩選，每一列只顯示中繼資料——標籤、派生狀態、已核銷次數與上限、簽發／到期／（被撤銷時）撤銷時刻——絕不顯示碼本身。簽發必經確認框，之後在一個可選取的一次性展示格裡給出完整邀請碼：介面不自動複製、不擺分享鈕、不畫二維碼，所以丟了只能重新簽發而非讀回（伺服器只存它的雜湊）。撤銷點名該碼、說明它只擋住之後的核銷、是單向的、不是刪除；重複撤銷拿到 2022 並只給一個重讀出口。這張卡只管憑證——簽發、名冊與撤銷——它自己不核銷任何碼：核銷是註冊畫面那一側的事（門外的人拿自己的碼走 `POST /auth/register`），把策略切成 invite 則是另一張策略卡單獨的決定。這道分工是刻意的，不是一條缺失的通路——Root 在這裡簽出的碼，一旦策略設成 invite，就能在註冊畫面上被核銷。開設表單交出去的是三個值——登入名、顯示名稱與一次性初始口令——請求裡沒有角色或主體類別的格子，因為「建的是管理員」由端點決定。初始口令不再回顯、不寫入任何本地快取，介面任何一處都不會出現它；新建立帳號首次登入必須把它換掉，換掉之前伺服器本來就擋住其餘受保護入口（專用機器碼 2010）。重設憑據走的是同一套做法：Root 在一個遮罩輸入框裡鍵入替換口令，送出即清空，介面從不回讀，確認對話框在請求發出之前講清這次重設會做什麼。目錄是真正的分頁檢視而不是定長短清單：翻頁與總數由伺服器回顯、只有一種狀態篩選（已刪除的也列出來）、依授予時刻由新到舊排序，而配置的 Root 依設計永遠不會成為其中一條可編輯的行。點開一行會先按標識從伺服器重讀這筆單筆資料，編輯表單才出現；表單只改顯示名，並且連同所見過的現值一起提交——對著過期畫面的儲存會被拒絕（2013）且什麼都不覆寫。停用要先經確認對話框：點名目標、講清影響（新登入被拒、其名下現有會話全部撤銷）與不會發生的事——這不是刪除。恢復只恢復重新登入的能力：停用時撤銷的會話不會復活，尚未完成的首次改密要求仍然有效。刪除是另一條終態通路，也自帶確認對話框：點名帳戶，在送出之前講清後果——登入停止、現有會話撤銷、沒有恢復入口。停用與刪除是兩種狀態，所以恢復登入永遠不會讓已刪除帳戶復生，介面上也不會有那樣的按鈕。已刪除的記錄轉為唯讀：顯示伺服器寫入的佔位顯示名與刪除時刻，並說明歷史操作背後的身分仍然可解析，因為授予、會話與稽核仍指向同一個帳戶。配置的 Root 憑據不是目錄裡的一列，因此在這裡永遠不構成刪除目標。這個介面上不存在「停用 Root」或「管理員停用其他管理員」的提交路徑；對著過期依據或重複的狀態變更會被 2014 拒絕，介面給的是「重新讀取再看」，不是再點一次按鈕；對已刪除的帳戶發起編輯、重設憑據或再次刪除都會被 2015 拒絕，而任何刪除在結果不明時都不會自動補發。介面顯示的每一個數字與標籤都來自服務端回應，不做樂觀填充。第七項是一張策略卡：它現讀三個值（管理員可否建立一般帳戶、自註冊模式、可否建立訪客帳戶），保存之前必經確認對話框。畫面把兩件事分開講——保存下來的是這個部署的意圖，而「管理員建立一般帳戶」「自助註冊」「邀請碼」與「訪客進入」這四條通路現在都已存在，所以每一列都如實跟著那個開關走，不再有一條是因為背後還沒實作而永遠是關；模式給 closed、open、approval 與 invite 四個選項，approval 收下的是在批准之前不能登入的申請，卡上如實說出批准的含義（審批在管理員端的註冊申請畫面上進行，那裡任何決定都發不出伺服器級角色）；invite 只讓持有效碼者自行註冊，卡上也說明這枚碼按帳戶逐次核銷、發不出任何伺服器級角色、換出的帳戶與開放模式一樣可立即登入。這張卡還給不出的模式（未來多出的名字）會照伺服器原字顯示、不悄悄改名，而列在這裡的選項必須與後端真的接受的那些同步：清單少一個寫得進的模式，保存另外兩欄時就會把伺服器記錄的模式頂掉。讀不到時卡片不顯示任何猜測值，寫入失敗時三個值都回到上一份伺服器真相，結果不明時不會自動補發。
- 管理員端今天接線了十項能力：建立一般帳戶、翻閱一般帳戶目錄、讀取與維護單筆基礎資料、停用與恢復一般帳戶的登入、重設一般帳戶的登入口令、批准或拒絕一份註冊申請，把訪客帳戶就地升級為正式帳戶，為訪客執行唯讀的綁定預檢（它絕不綁定任何人），簽發這條唯讀預覽旁邊唯一會寫資料的操作憑證（它是管理端對一次綁定唯一能交出去的東西），以及軟刪除一般帳戶與訪客。表單交出三個值——登入名、顯示名與一次性初始口令——沒有角色、帳戶類型或活動的欄位，因為「新建的是普通帳戶」由端點決定：不帶任何伺服器級授予，也沒有任何活動檔案或資產。開關開沒開不做預讀：伺服器在建立交易的同一筆快照上現讀策略，開關關著時回機器碼 2017（與 2011 那句「沒有權限」是分開的兩句話，Root 走這條端點也一樣被擋），名字被佔用回 2012，成功卡會明說帳戶已建立但還不屬於任何活動。初始口令不再顯示、不存在任何狀態裡、也不出現在介面任何一處；新帳戶首次登入必須改密，受與所有帳戶相同的服務端門閂（2010）約束。
- 一般帳戶目錄今天可以翻閱與維護：分頁目錄依狀態（全部／啟用／已停用／已刪除）、來源（全部／普通帳戶／訪客帳戶）與名稱關鍵字（比對登入名與顯示名兩欄）篩選，翻頁與總數一律取服務端回顯；點一行會先依標識從服務端重讀這筆單筆資料，編輯表單才出現；已處於終態的那一列重讀回來是唯讀的，表單不再出現。已刪除的行仍然列在這裡，並帶著服務端寫入的刪除時刻（從沒被刪過的行沒有這一欄），好讓歷史身分仍被查到；這本目錄列不到管理員，也列不到 Root——持有伺服器級授予的人歸 Root 的管理員目錄，兩本目錄彼此互斥；沒有管理權的會話讀它只會拿到「沒有權限」（2011）而不是一個空清單，匿名則是 2002。表單只改顯示名，並且連同所見過的現值一起提交——對著過期畫面的儲存會被拒絕（2013）且什麼都不覆蓋，介面給的是「重新讀取這份資料」，不是再點一次儲存；登入名不在這裡修改，憑證、權限與安全狀態也不在這張表單上（本體裡多帶任何隱藏欄位都會被服務端打成 1004）。單筆詳情沒有活動、資產與訊息這三塊：那些模組尚未實作，介面不拿空清單或 0 冒充查得到的真相。標識格式不對、帳戶不存在、他是管理員、他還在審批鏈門外，四種輸入都收到同一個 1001，這根端點因此不是「某人是不是管理員」的探針；刪除與退休兩種終態刻意不在這個回答裡——那一列讀得到，只是動不了。
- 一般帳戶的登入停用與恢復接在同一張單筆詳情卡上，介面先把範圍講清：這裡動的是這個帳戶在這台伺服器上的登入能力，不是某一場活動裡的玩家限制——停用會拒絕他今後的登入，並撤銷他在每台裝置上的現有會話。送出之前必經確認對話框，它點名目標、講完影響範圍與「這不是刪除」；取消時一個請求都不發。按鈕只由服務端讀回的現狀決定（啟用中只給停用、已停用只給恢復、認不出的值只說一句話，不猜方向），依據值取上一次從服務端讀到的現狀，因此對著過期畫面的儲存會被 2014 拒絕且什麼都沒發生，介面給的是「重新讀取這份資料」，不是再點一次按鈕。成功後介面把狀態、停用時刻與「這次讓幾個會話退出」全部換成服務端回應，並重新讀取目錄；恢復只恢復重新登入的能力——停用期間被撤銷的會話不會復活，還沒完成的首次改密仍然被 2010 擋著，已被刪除的帳戶更不能這樣恢復。訪客帳戶走同一組控制項，因為這本目錄的定義就是「不持有伺服器級授予」。活動內的禁言、交易凍結與陣營限制不在這裡，也沒有被偽裝成可用。
- 一般帳戶的憑證重設接在同一張單筆詳情卡的第三條白名單上：`PUT /admin/accounts/{account_id}/password`，請求本體只有 password 一欄，而且刻意沒有依據值——操作者拿不出「現行雜湊」這類誠實的錨點，所以對著不明的結果再按一次那顆按鈕不是重試，而是又做一次完整的重設（再撤一輪可能新簽發的會話、再留一筆稽核）；介面因此自來不自動補發。交付沿用 Root 那側已核准的方案：口令由管理員親自交、伺服器不生成也不回顯、不設預設口令，輸入框遮蔽、在請求發出前就清空，成功句只講這次讓幾個會話退出與「線下交付、首次登入必須改密」，那串字之後不再出現在介面任何一處，也不進日誌、稽核、可讀偏好或自動複製的剪貼簿。停用中的目標照樣可以重設（重設不是解除停用），介面不按狀態分岔；重設不動停用、不動刪除終態，也不會免掉他欠的那次改密——今天沒有帳戶級審批狀態，「待審批」如實就是「欠首次改密」，重設寫的是「必須改」而不是「不用改」。訪客帳戶在這條通路上出局：他本來沒有一般密碼，替他寫一個進去等於把他的身分升級成普通帳戶，那該走同一張卡上的訪客升級區；介面據此不擺那顆按鈕、只這一句，伺服器也以機器碼 2018 回答同一句話。權限不足（2011）、目標不在這本目錄（1001）與口令不合規（1004）各說各話；介面裡的每一個數字與狀態都來自服務端回應，不做樂觀填充。
- 訪客的就地升級接在同一張詳情卡的第四條白名單上，只有服務端讀回的來源欄位說他是訪客時才會出現。`PUT /admin/accounts/{account_id}/upgrade` 的本體只有正式登入名與一次性口令兩欄，沒有帳戶類型、角色、狀態或旗標的格子：升級出來的形態恆為「仍欠首次改密的普通帳戶」，由端點決定而不是由請求決定，介面上連「升成管理員」都寫不出來。發送之前，卡片把兩處分野講清：這是就地轉正，保留同一個帳戶標識、顯示名與全部歷史記錄——不是新建帳戶再把訪客刪掉，也不是把他綁到另一個既有正式帳戶（那條執行通路今天還不存在，介面能給的只有唯讀預檢，見下一條）；確認對話框唸出目標與新的正式登入名。口令與重設同規：遮蔽欄、在請求發出前清空、不回顯、結果不明絕不自動補發。成功句的撤銷數量取自服務端回應：升級在同一筆交易裡撤銷舊訪客憑據名下的全部會話——這是本步批准的決定，撿到舊臨時令牌的人不會靜默變成正式帳戶——回到門內的唯一方式是用新憑據真實登入一次，而首次登入立刻被要求先改密的門閂（2010）擋下。成功後介面跟著服務端回的記錄走：訪客控件收起、憑證區如實出現、目錄重讀。停用中的訪客不給升級鈕，只給「先恢復他的登入」那一句；目標已轉正或此刻被停用回 2024，名字被佔用回 2012 而訪客那一行一個字都不改；訪客本人來敲這條端點拿到的是 2011——這條只有管理員走得通的路，存在的意義之一就是答不了他。
- 訪客綁定預檢以唯讀預覽的形式接在同一張詳情卡上：`POST /admin/accounts/{account_id}/bind-preflight` 的本體只有目標帳戶標識一格，一次只評估「這個訪戶 × 這個目標」的一對——不存在替訪戶羅列可綁定目標的讀法，這張畫面不是尋人工具。它純唯讀、零寫入：不改帳戶、不撤會話、不動授予，也不寫一筆審計；結果面板第一句顯著標示「這只是預檢結果：尚未綁定」。服務端回來的是 200 預覽而不是錯誤：不可綁定時以穩定原因記號逐條點名——同源自同一對、來源已轉正或已退休、來源停用中、來源帶著伺服器級授予（形態缺陷方向）、目標也是訪戶、目標停用中，以及預檢尚未接入的帳戶引用（一旦出現，一切綁定整體被阻止，直到對應模組接入；未接入的表名只進伺服器日誌）。回應還帶出該訪戶名下有多少會話會在執行時登出、這份預檢按哪一版資料庫執行，以及恆為 target_self_initiated 的同意形態：將來綁定也只能由目標帳戶持有人以自己的已認證會話發起，管理端永遠拿不到代他人完成綁定的按鈕，而那條執行通路今日不存在。來源或目標不在目錄收斂成與詳情同句的 1001，訪戶本人拿 2011，目標標識缺失或壞形拿 1004 點名欄位——預檢本身不發布任何屬於它自己的新機器碼。
- 簽發綁定憑證是同一張詳情卡在那條唯讀預覽旁邊的唯一一條寫入白名單：`POST /admin/accounts/{account_id}/bind-ticket` 的本體同樣只有目標帳戶標識一格，而伺服器在簽發事務裡把整份預檢重跑一遍——預檢通過不等於之後永久有權執行。它回給你一枚 22 字元的明文，只在這一屏出現這一次：它釘住這個來源訪戶、這個目標帳戶、這份計劃與計劃所依據的資料庫版本，15 分鐘後自動失效，花掉第二次在結構上根本不可能——「重複請求、換目標和重放不能改變其他帳戶」在這裡是庫裡的約束，不是一句承諾。明文不落地任何本地快取，也不進日誌、審計、偏好或自動複製的剪貼簿；審計如實記下的是「誰為這一對簽發了憑證」這件事本身，它是這次身分遷移的第一段不可變留痕。按下它必然先出確認框，框裡點名被准許的目標並明說這不是綁定本身：這一動不退休訪戶、不登出會話、不追加歷史，管理端也永遠不會拿到代他人完成綁定的按鈕。若預覽之後實況變了（冒出一張本預檢尚未登記的帳戶引用表、這一對裡某一方的身分或登入能力改了、資料庫版本推進了），伺服器回新機器碼 2026 並逐條帶出原因記號，一個位元組都不寫；2026 那句話給出的處置是重新預檢、憑新憑證再確認，而不是把這一顆再按一次。1004 照舊點名欄位，1001 與 2011 各說各話，取消則一個請求都不發。
- 綁定由目標帳戶本人在已登入的會話卡上執行，而這個入口只為「普通正式帳戶、不是 Root、不持有伺服器級授予、且不欠首次改密」的主體出現：把憑證貼進去先做一次唯讀回顯，畫面唸出這份憑證准的是哪個訪戶、目標是不是你自己、五條影響與失效時刻；只有另一顆需要單獨確認的按鈕才會真的花掉它。伺服器在那一個事務裡做的事是：撤銷該訪戶名下的全部會話、把這個訪戶帳戶推進到一個新的終態（retired——既不是停用也不是刪除，他的登入名繼續被佔著，誰也無法再以那個身分登入），保留他的身分與每一條過往記錄可被查明（歷史不會被改寫成「從來就是目標帳戶」），並從此把新的歸屬記到目標帳戶名下。沒有任何東西在背後被複製或合併：目標保留自己的口令、授予、狀態與資產，不搬動任何餘額或帳本分錄，目標自己的登入能力也原樣不動——一枚花掉的憑證永遠不等於換成一枚能登入別人帳戶的令牌。已被核銷、已過期或不是釘住這一對的憑證一律回同一句 2025，這句話故意不說它是哪一種，這個入口因此不是替別人試探憑證的探照燈。綁定會撞上本機尚未接入預檢的業務引用時，伺服器拒絕並說明限制（2026），絕不為了讓檢查通過而刪資料。執行失敗時原先可用關係一條都沒動，介面如實說失敗；提交成功後回應丟失時介面報「結果待確認」而不重發，另有一張唯讀清單（`GET /auth/guest-bindings`）列出已經併入本帳戶的綁定，用它查實際結局。失敗、已完成與結果待確認因此是三句不同的話，一次不明的結果永遠不會被點成第二次遷移。
- 一般帳戶與訪客的軟刪除接在同一張詳情卡的最後一條寫入通路上，而畫面先把範圍說清：這裡動的是這個帳戶在這臺伺服器上的登入能力，不是某一場活動裡的玩家限制——那句話常駐在按鈕之前，按下去之前就讀得到，不是確認框裡的附件。`DELETE /admin/accounts/{account_id}` 不帶任何請求本體：`{}` 可以，多帶任何一個欄位（包括理由文字，也包括依據值）都回 1004，而這條通路刻意沒有依據值欄位——「現行刪除時刻」對操作者不是一個拿得出的錨點，權威是狀態機守衛，所以第二次刪除寫不中任何東西、被拒而不是報成功。確認對話框點名目標（登入名、來源類型與服務端讀回的現況），講完三件會發生的事（新的登入被拒、他此刻持有的全部會話被登出、顯示名換成服務端寫入的匿名化佔位值）與兩件不會發生的事（這不是停用——被刪除的帳戶沒有復原入口；而登入名繼續被佔用，別人搶不到這個名字），並說明帳戶行為什麼是刻意留下的：既有稽核與歷史要仍能指向同一個人。取消時一個請求都不發，畫面上也沒有「我已瞭解」的勾選框——那個對話框本身就是最後一道把手。成功之後這張卡退出編輯態：改名框與每一顆寫入按鈕全部消失，只列服務端回的刪除後真相、帶著刪除時刻的唯讀橫幅，而「這次讓幾個會話退出」的數字來自回應，不是畫面猜的。兩種終態一律唯讀：`deleted` 與 `retired` 的那一列上，編輯表單、停用／恢復、口令重設、訪客升級、綁定預檢與憑證簽發全部收起，卡片只列服務端說的事實。已被刪除的回 2027、已被綁定併入他人名下的訪客回 2028（此前這張卡會給一個已退休的訪客擺出改名框，而那次寫入在服務端被拒絕）；退休那一列該讀的是綁定留痕——他沒有消失，他以被綁進去的那個帳戶繼續存在。兩句都只給「重新讀取這份資料」這一個出口，不給「再按一次」；結果不明時永不自動補發，刪除到底有沒有發生，由重讀目錄與詳情來回答。這本目錄按定義列不到持有伺服器級授予者與配置 Root，所以普通管理員刪除不了另一位管理員，也刪除不到 Root——那些標識與格式不合法的標識、幽靈標識一律收斂成同一句 1001，這條端點不是標識探針。物理清庫、批次刪除、帳戶自助註銷與自動清理舊訪客都不存在，畫面也不假裝它們存在。
- 註冊申請在管理員端有自己的一頁。`GET /admin/registrations` 列的是還在等的與已經被拒絕的：每一行只有登入名、顯示名、狀態、提交時刻，以及在已有決定時的決定時刻，沒有別的。這就是審核需要的全部事實；畫面上沒有憑據、沒有會話材料、也沒有角色欄，而普通帳戶目錄仍是另一本書、有自己的範圍條件。兩顆按鈕只在服務端回傳的確為 `pending` 時出現；已經被拒絕的那一行改給一句實話——決定在這裡是單向的，沒有任何通路能重開，而那個登入名繼續被佔用。兩顆按鈕旁邊都沒有理由輸入框：內部備註與可公開理由都不落庫，擺一個填了會被悄悄丟掉的格子只會更糟。確認對話框點名目標，並說清落下什麼（一個能用自己的口令登入、不帶任何伺服器級角色的普通帳戶）與不會發生什麼（不替他簽發會話、不解除任何停用、不改名也不刪除）。成功句取自 PUT 回應——落地的是哪個決定、是誰的申請——隨後重讀名冊而不是本地改那一行，因為被批准的人已經不在這本書上。2021 說這份申請已有決定：介面只給重讀這一個出口，結果不明時絕不把決定再發一次。1001 說目標根本不在這本名冊，2011 說這個會話不能對任何人做決定——三種處置各自成句。這一頁不做任何通知：這台伺服器沒有通知模組，申請人只能重新出示自己的憑據，在狀態查詢那頁看到結局。

- Root 管理模組的其餘部分仍在開發：已登入的主頁只呈現真實身分與此刻真正可用的入口，不會用示例數據冒充。身分那一行依伺服器回傳的 `roles` 顯示，管理員看到的是「伺服器管理員」，沒有授予的帳戶看不到；管理員自己打開同一張表單，只會收到「沒有權限」那一句（機器碼 2011），重新登入也不會讓它變成可用。原生客戶端的會話憑據保存在系統級安全儲存，瀏覽器路徑由 HttpOnly Cookie 代管，絕不明文落盤。瀏覽器路徑那枚 Cookie 只在頁面確實經 HTTPS 提供時才標 Secure；區域網明文 HTTP 部署下，瀏覽器的防線由 SameSite 加伺服器的來源判定承擔，要用 HTTPS 就得在伺服器前面自行加一層終結 TLS 的反向代理。

## 伺服器位址

伺服器入口頁可以直接輸入要使用的伺服器位址並儲存在本機，切換測試伺服器不必再重新建置。只接受完整的 `http://` 或 `https://` 位址（不得包含使用者名稱或密碼），而且必須連得通才會儲存：格式不合格時依具體原因提示（例如「位址要以 http:// 或 https:// 開頭」），並且完全不發出請求；格式合格但連不通時不儲存，改由介面說明原因，不會假裝成功。介面把「目前使用的位址」與「本機已儲存的位址」分開列出，並說明目前的值從何而來；除錯建置下建置參數 `--dart-define=ER_SERVER_BASE_URL` 優先，此時介面會明確告知本機儲存的位址尚未生效。你輸入的內容只儲存在自己的裝置上。

## 介面出錯時

如果應用某一部分無法正常顯示，介面會切換到一個安全的提示頁面：說明問題發生的位置（介面繪製、背景工作或與伺服器往來）、一個用於對照本機日誌的診斷碼，以及伺服器請求的關聯 ID（若與請求有關）。你可以按「返回可用頁面」回到可使用的介面。提示頁面不會顯示錯誤原文、程式堆疊或伺服器位址，也不會把任何內容傳送到外部——問題只記錄在你自己的裝置上。

需要說明的是：剛出錯的那一塊在返回後可能短暫留白，要等介面下一次重建才會恢復；若同樣的問題反覆出現，提示頁面會建議你重新載入應用。

## 從原始碼建置

各平台圖示與啟動畫面是產生出來的、不納入版本控制：它們由 `assets/icons/` 下的四張來源圖推導。全新複製的倉庫在建置前先執行

    python tools/icons/generate_icons.py

缺圖示資源時 Android、iOS、macOS 與 Windows 建置會直接失敗，Web 建置則會沒有圖示。`python tools/icons/generate_icons.py --check` 只核對現況，不寫入任何檔案；詳見 `tools/icons/README.md`。
