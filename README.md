# EvernightRealm Web

> The client interface of EvernightRealm — step into your group's private world from a browser or desktop app.

[English](./README.md) · [简体中文](./README.zh-CN.md) · [繁體中文（台灣）](./README.zh-TW.md) · [日本語](./README.ja-JP.md)

## What is this?

This is the client of EvernightRealm, a self-hosted, offline-first platform for a small group of players. Activities, characters, assets and chat all come to life here, on a local network — no internet, cloud accounts or telemetry.

## Features (under development)

- **Activity view** — follow scenes, phases and events as they unfold
- **Character panel** — play player, NPC and admin identities in one private world
- **Asset management** — see and trade virtual items with auditable ownership
- **Private chat** — messages stay on your own server
- **Offline-first** — the client works fully against your local server; no cloud required

## Current status

Under active development. No stable release is available yet. The identity stage is wired end to end in this client today: the server-entry screen (saved address, connectivity check, the read-only Root-initialization card and the guest door), sign-in, sign-up in all three registration modes, the applicant's own status lookup, self-service session/device/password management, the Root console (nine capabilities, including activity management and assigning or revoking an activity's managers) and the administrator console (eleven capabilities, including creating an activity, its directory, name/description editing, the open/stop/reopen/archive transitions, faction management inside an activity — list, create, edit, reorder, and disabling or re-enabling a faction through a per-row button whose confirmation reads out the impact summary — and the activity's member roster — list who joined, add an existing account, and edit his nickname inside that activity, plus the target owner's guest-binding card. The player surface is wired for two things and says so: it lists the activities where the signed-in account has a member row, lets that player pick his own faction where the activity opens self-selection, and now also carries the player directory - a paged roster, a nickname search, faction facets, an authorized single lookup, and the own-profile section that still reads back when the directory is closed; while the NPC console still renders an honest “not wired yet” placeholder. An activity you manage is a real container whose contents today are the factions you create, the members you add and the tag definitions you maintain (a per-tag flag decides whether that activity's members may read the definition itself; attaching a tag to a player is not implemented), assigning members to factions from the management side, plus assets and chat, are still not implemented — nothing is padded with sample data. The authoritative quick reference for every account operation — who may run it, how it refuses, how credentials are handed over — is the “Account operations at a glance” section of the backend repository README; the sections below describe the same contract from the screen side.

## How it will work (once released)

- Open the host's address in a browser on the same local network — no install needed
- A desktop app will also be available for Windows, macOS and Linux
- No third-party registration; data stays on the host's machine

## Languages

Simplified Chinese, Traditional Chinese (Taiwan), English and Japanese. The interface language follows your system language by default and can be switched on the server entry page; the choice is remembered locally. System languages outside this list fall back to English.

## Server connectivity check

The server entry page offers a server connectivity check: it reads the health and time endpoints from your server and shows the service name and version, the server's UTC time, that time converted to the server's own display timezone, and the request ID for the call. When a check fails, the interface states only why it failed (unreachable, no response, service not ready, and so on) together with the error code and request ID — nothing that looks like a successful result is left on screen. Every value comes from the server; the app never falls back to the device clock or sample data.

## Root initialization guide

A brand-new server has no Root yet, so the entry page carries a read-only "Root initialization" card. It asks the server for its initialization state and shows exactly one of five honest results: not initialized, already initialized, server unreachable, server refuses to report, or this check produced no reliable answer. (With no saved address it says that first and sends no request at all.) The steps to run on the server's own machine — stop the service, create the schema first if the data directory is brand new, run `evernight-server init-root --password-stdin`, start the service again, then check again here — appear only when the server actually answered "no Root yet". A failed check is never phrased as a state, and "Check initialization" only asks again: every call is read-only and cannot create, change or overwrite a credential.

The card collects no password. It has no password field and sends no credential anywhere, because initializing Root remains reachable only through a command run on the server host. Once a credential exists the card stops listing steps and simply reports initialization is complete; signing in is now available through the "Login and session" card below, while this card itself stays read-only and collects no credentials.

## Sign-in and identity restoration

Once the server has a Root, the entry page's "Login and session" card is the way in:

- The sign-in page first shows which server you are about to sign in to (the effective address, plus service name and version when a probe succeeded), then asks for credentials. Two paths exist: Root sign-in (password only) and account sign-in (login name plus password). The account path reuses the existing server endpoint. Accounts come into existence through three entries: Root opening administrators in the Root console, administrators creating ordinary accounts in the administrator console while the server's account-creation policy keeps that path open, and - while the policy offers it - anonymous self-registration on the sign-up screen, which never signs anybody in by itself. Self-registration now runs in all three shipped modes: open, approval, and the invite-code mode (the sign-up screen reads the server's `invite_code_required` answer and reveals an invite-code field only in that mode, then hands the code to the same `POST /auth/register`, which redeems it into an ordinary account). Guest entry is offered now, as the restricted path it is: a separate card on the server-entry screen reads the server's `guest_open` answer, and only a press of its own button creates the temporary identity — loading, refreshing and reconnecting never write anything.
- Every failure says its own honest piece: refused credentials map to one uniform sentence (the server does not distinguish "no such account" from "wrong password", and neither does the interface), throttling says to try again later, unreachable and local-storage failures each say their own. No message ever echoes your password, the server's own text is never displayed verbatim, and nothing is saved or auto-filled on this device.
- After signing in, the identity shown is the one the server confirmed — never whatever the form guessed. Protected pages sit behind a session gate that shows nothing protected before the server answers, and the "return to" target kept when you are bounced to the sign-in page can only be a route registered in this app; anything else (including external URLs) lands you back on the entry page.
- Reopening the app restores and verifies the previous session first: while checking, only a neutral hint appears; if the session is still valid the card lists the real subject, device and server-side expiry (UTC); if the server deems it invalid you are returned to sign-in and the stored credential is cleared.
- The signed-in card carries a Sign-out button that makes the server revoke exactly this session: on web the response delivers a delete instruction with the same cookie name and attributes, on native the stored credential for this server is removed from system-level secure storage. Signing out again is idempotent—the server does not open a new session or tell you to sign in again just because the credential was already dead. When the server cannot be reached, this device still clears its own state, and the notice separates "local cleanup done" from "server revocation unconfirmed"; it never claims the server signed you out, and it never implies every device has gone offline.
- The signed-in card also carries a My-devices entry: it lists your own sessions exactly as the server reports them, marks the device you are using right now, and lets you revoke another one. The scope is enforced by the server — the panel cannot name another account's device — and revoking the current device is the same as signing out on it. A stale list, an already-invalid session and an unreachable server are each stated as they are; a revocation that did not happen is never reported as success.
- The signed-in card also carries a Change-password entry: rotating your credential requires handing over the current password in the request itself—“still signed in” is never authorization for a password change. A successful change revokes every session of yours, this device included (the approved policy), and the app enters the signed-out state asking you to sign in again with the new password. No password is cached anywhere: the three fields live only inside the dialog, are cleared when used, and every field is obscured. For accounts flagged “must change password at first sign-in” the server itself only serves the change-password flow, sign-out and the current-session read; every other protected feature answers machine code 2010. The card then shows only those entries instead of pretending buttons that are certain to be refused would work.
- The sign-up screen is a door for people who are still outside it. It appears on the entry page only when the server's anonymous capability answer (`sign_up_open`) says the self-registration path is open, and it collects login name, display name and a password the person chooses themselves - plus an invite-code field that the server's third boolean (`invite_code_required`) reveals only in invite mode. The invite code is a transient secret: it is typed into one field, sent only in that request body, never placed in the address bar, browser history, logs or any cache, and cleared with the other fields on success. There is no control anywhere on that screen for a role, an account type or an approval state, because the endpoint - not the form - decides what kind of subject appears, and a request carrying such a field is refused by the server before anything is written. Showing the door is never a promise of admission: the server re-reads its own policy inside the writing transaction, so a switch Root flipped in the meantime cannot be walked through with a stale screen, and a hidden invite field never bypasses the "invite mode needs a code" check.
- What a submission leaves behind depends on the mode the server is running, and the screen only reports the answer it got. With `open` it gets an account that can sign in immediately with the password just chosen, and the summary says so. With `approval` the same three fields file an application instead: the account exists, its login name is taken, its own password is stored - and it cannot be signed in to until somebody approves it. The screen then says plainly "application submitted, not yet approved" and offers no sign-in shortcut it knows will fail. With `invite` a valid code, redeemed inside the same transaction that creates the account, lands an ordinary account that can sign in immediately - the summary reads exactly like open mode, because the sign-in behaviour is the same; a code that cannot redeem (missing, malformed, revoked, expired, used up, or lost to a concurrent sign-up) is refused with one non-leaky sentence, code 2023, that deliberately does not say which half failed. The anonymous capability answer deliberately keeps naming no mode, so this is decided by the server's write, never guessed by the interface.
- An applicant can ask how their own application stands on a separate screen that is not a login. It re-checks the credentials for every query (login name and password in a POST body, never in a URL) and answers with just the outcome - still waiting, approved, or declined - the submission time and, once a decision exists, the decision time. It issues no session and stores nothing: no cookie is set, no token is kept, reloading or leaving the page leaves nothing that could be reused, and there is no queue position, no reviewer name and no reason text, because those are the server's own business. Somebody approved there is sent to the ordinary sign-in page; nothing about this path makes an account usable earlier.
- Repeated submissions under the same login name are refused with the same uniqueness answer as anybody else's - an application keeps occupying the name, and so does a declined one. A person who was declined therefore cannot submit again under that same name, and neither can anybody else. Switching the server's mode afterwards changes nothing about applications already filed: they are neither waved through nor thrown away by a policy switch, only by an explicit decision, which somebody makes on the application screen of the administrator console.

- A separate card on the server-entry screen is the guest door. It appears only when the server's anonymous `guest_open` answer says the guest path is open, and — unlike the sign-up screen, which never signs anybody in — pressing its button both creates the temporary identity and hands over a session: `POST /auth/guest` returns a session cookie exactly as sign-in does, so the browser keeps it in the HttpOnly cookie and a native client puts it in platform secure storage. The nickname field is optional and is display information only; leaving it blank gets the server's own temporary code, and the card states that before anything is sent. The card also states its own limits: this identity belongs to no activity, carries no server-level grant (administrator and Root screens answer it 2011), and has no password to change — which is why the signed-in card offers a guest no change-password entry, only the devices, rotate and sign-out entries that genuinely work — and when the session expires, you sign out, switch device or clear local credentials, this visit ends. There is deliberately no "recover by nickname" screen: a name you can type is not a credential, and what happens to that account is an administrator's decision after verifying the person in the ordinary-account directory. Nothing is created by loading, refreshing, reconnecting or a failed re-check — only by that one button, and repeated presses while it is in flight send a single request. Where you land afterwards is the player surface, which says plainly that this identity belongs to no activity yet, while the identity line reads "guest (temporary identity)" straight from the server's `account_type` — so a refresh or a restart still tells the truth.

- The Root console wires nine capabilities today: creating a server administrator, browsing the administrator directory, viewing or editing one record, disabling or restoring an administrator's sign-in, resetting an administrator's sign-in credential, soft-deleting an administrator, the server's account-creation policy, and managing server registration invite codes. The creation form hands over three values - login name, display name and a one-time initial password - and there is no field for a role or a subject kind, because the endpoint is what makes the account an administrator. The initial password is never shown again, never cached locally and never appears anywhere in the interface; the new account has to change it at first sign-in, and until it does the server itself refuses every other protected entry with code 2010. A credential reset is handled the same way: Root types the replacement into one obscured field, the field is cleared as soon as it is submitted, nothing is ever read back, and a confirmation dialog states what the reset does before the request goes out. The directory is a real page view, not a fixed short list: paging with a server-echoed total, one status filter (deleted accounts are listed too), newest grant first, and - plainly stated by design - the configured Root is never one of its editable rows. Opening a row re-reads that single record from the server before the edit form appears; the form edits only the display name and submits it with the stored value it saw, so a save based on a stale screen is refused (2013) and overwrites nothing. Disabling asks for an explicit confirmation that names the target, says what it does (new sign-ins rejected, all their live sessions revoked) and what it does not do - it is not deletion. Restoring only brings back the ability to sign in again: sessions revoked when the account was disabled stay dead, and a pending first password change stays required. Deletion is its own terminal action behind its own confirmation, which names the account and states the effects before anything is sent: sign-in stops, live sessions are revoked, and there is no restore - disabled and deleted are two different states, so the restore entry can never revive a deleted account and the interface offers no such button. A deleted record goes read-only: it shows the placeholder display name the server wrote and the deletion time, and it explains that the identity behind past operations is still resolvable, because grants, sessions and audit rows keep pointing at the same account. Root's own configured credential is not a directory row, so it is never a target here. Neither Root nor one administrator disabling a peer can be submitted from this interface at all, and a stale or repeated status change is refused with 2014, which the screen turns into "reload and look again", never a second click; editing, resetting the credential or deleting an already-deleted account is refused with 2015, and nothing that deletes is ever re-sent on an unclear outcome. Every number and label shown comes from server responses; nothing is filled in optimistically. The seventh is the policy card: it reads the three values from the server (whether administrators may create ordinary accounts, the self-registration mode, whether guest accounts may be created) and requires a confirmation dialog before saving. The screen keeps two facts apart - what is saved is this deployment's intention, while the four paths behind those switches - administrator-created ordinary accounts, self-registration, the invite code and guest entry - all exist now, so each line follows its switch and none of them stays closed by missing implementation. Mode offers closed, open, approval and invite: approval files applications that cannot sign in until somebody approves them, and the card says out loud what approving means (applications are decided on the administrator console's application screen, and no decision there can hand out a server role); invite lets only a holder of a valid code sign up on their own, and the card says that code is redeemed per account into an ordinary account with no server role, on the same immediate sign-in path as open. A mode this card cannot yet offer (a future name) is shown as the server's own value and is never silently relabelled, while the choices listed here stay in step with what the server actually accepts - a card that offers fewer modes than the server accepts would overwrite the recorded mode every time it saves the other two switches. When the card cannot read the policy it shows no guessed values, a failed write returns all three values to the last server truth, and an unclear outcome is never re-sent automatically. The eighth is the invite-code card: it lists the codes Root has issued with paging and a status filter (active/expired/used-up/revoked) plus a label keyword, and each row shows only metadata — label, derived status, redeemed/total, the issued and expiry and (when revoked) revocation times — never the code. Issuing runs through a confirmation dialog and then reveals the full code exactly once in a selectable field: the screen copies nothing, shows no share button and draws no QR, so a lost code is re-issued rather than read back (the server keeps only its hash). Revoking names the code and states that it only stops future redemptions, is one-way, and is not a delete; a repeat revoke gets 2022 and offers only a reload. This card manages the credentials only - issuing, the roster and revoking - and never redeems a code itself: redemption is the sign-up screen's job (an outside person brings their own code to `POST /auth/register`), and switching the policy to invite is the separate policy card's decision. That separation is deliberate, not a missing path - a code Root issues here can already be redeemed on the sign-up screen once the policy is set to invite. The ninth is activity management: Root sees every activity regardless of assignment, and this is also the only side that can assign or revoke an activity's managers, because that is a privilege grant.
- The administrator console wires eleven capabilities today: creating an ordinary account, browsing the ordinary-account directory, reading and maintaining a single record's basic profile, suspending or restoring an ordinary account's sign-in, resetting an ordinary account's sign-in credential, approving or declining a registration application, upgrading a guest account in place to an ordinary one, running a read-only binding pre-check that links nobody, issuing the short-lived single-use ticket that is the only thing this side can hand towards such a binding, and soft-deleting an ordinary account or a guest. Deleted rows stay listed here, carrying the server's deletion moment (a row that was never deleted simply shows no such line), so a past identity can still be looked up. The form hands over three values - login name, display name and a one-time initial password - and there is no field for a role, an account type or an activity, because the endpoint is what makes the new account an ordinary one: no server-level grant, and no activity profile or assets. Whether the path is open is not previewed anywhere; the server re-reads its policy inside the creating transaction, answers code 2017 while the switch is closed (a sentence apart from 2011's missing permission, and Root passing through this endpoint is refused the same way), refuses a taken login name with 2012, and the success card says in plain words that the account has been created but belongs to no activity yet. The initial password is never shown again, never cached locally and appears nowhere in the interface; the new account must change it at first sign-in under the same server-side gate (2010) that governs every other account. The eleventh is activity management: create an activity, read the directory of activities assigned to this account, edit name and description, run the open/stop/reopen/archive transitions, read that activity's manager roster, and manage its factions (list, create, edit, reorder, and disable／re-enable from each row - the confirmation dialog reads out what disabling does and what it explicitly does not do, and says plainly that membership is not implemented rather than showing a made-up member count; assigning players into factions is not wired yet, so every roster row reads not assigned) - adding or removing managers is not on this side.
- The activity's member roster is wired on the activity detail card: it lists who joined (nickname, the account's display name and current state, and the faction field), adds an existing account as a member, and edits that member's nickname inside this activity. One account gets exactly one profile per activity - a second add is refused with 2035 and the existing row is never overwritten, so the way to change a person is to rename the profile you already have. Whether an account may join is read from the server: standard and guest accounts can be added, while a pending, rejected, deleted or retired account answers with the same code and sentence as an ID that never existed, which keeps this path from becoming an enumeration probe. The nickname is display only: it is not an ID, grants nothing, and two members of the same activity may share it. Every write passes the activity gate first - draft and active accept, stopped answers 2033 and archived 2029 while the roster stays listed and readable - and a rename based on a stale value loses to 2013 with only "reload this roster" offered. There is no path to take a member out and no path to point a row at a different person. The management side still cannot assign a faction either, so a row that shows one does so because that member picked it himself - which can only happen where that activity opens self-selection.
- The activity page gained a faction self-selection switch card, and the player surface gained its own card. The switch is one column of the activity taking exactly three values - off (the default everywhere, so no activity is opened without a decision), first-choice-only, and free switching - and each option spells out its own consequence before you pick it; saving goes through a confirmation and sends exactly `mode` plus the `expected_mode` it is based on, so a stale basis value answers 2013 and leaves only a re-read. Players never touch that card and get 2011. On the player side, `GET /player/activities` lists only the activities where the signed-in account has a member row, and the detail card reads back his own affiliation together with every faction of that activity, each carrying a server-derived `selectable`. A choice sends exactly `faction_id` and `expected_faction_id`: a player can set his faction but cannot clear it, and the closed and unqualified cases are refused by the server rather than merely hidden - 2037 while the activity keeps the switch off, 2038 while it is still a draft, 2033 and 2029 for stopped and archived, 2036 for a disabled faction, 2039 once a first-only choice is used up, 1001 for anybody who is not a member of that activity. After a successful write both this account's own state and the management-side card are re-read, so no screen keeps a private copy of what the switch currently is.

- The activity page gained a second setting card - player directory visibility - and each roster row gained a hide-only override. The directory mode is one column of the activity taking exactly four values: fully hidden (the shipped default, so no activity exposes its members to each other without a decision), same faction only (people who are not assigned yet cannot see each other, only themselves), all players except staff (the rows the server currently records as holding the staff grant are the ones hidden - never a nickname or a label), and all activity members. Each option spells out its own consequence before you pick it; saving goes through a confirmation and sends exactly `mode` plus the `expected_mode` it is based on, so a stale basis value answers 2013 and leaves only a re-read. The per-row override has only `inherit` and `hidden`: hiding someone from other players' directories does not remove him from the activity, does not move his faction, and does not make him disappear from his own view or from yours - those three sentences are printed before the button is pressed. Both writes live on the management side (a player reaching them gets 2011); a paused activity can still prepare its directory setting, while the override first passes the business-write gate (2033 stopped, 2029 archived). Three player-side reads are now live: the paged directory (list, search, counts and faction facets all come from one already-authorised set), a direct lookup under the very same policy, and the person's own profile, which does not consult the directory policy at all - so it still works when the directory is fully hidden. Every directory row carries in-activity facts only: member id, in-activity nickname, the faction name/icon/colour and the join time. Login names, account ids, display names, account status and "is this person staff" never leave it; the last two appear only in the management roster. This step publishes no new machine codes: no such activity, not a member, a row belonging to another activity and a row currently hidden by policy are one and the same 1001, while "this mode lists nobody" is an empty page plus the echoed mode rather than an error.
- The player surface gained a player-directory card wired to the three reads that already exist on the backend, without inventing a single new field. The list consumes only what the server has authorised: the roster, a nickname search, faction facets whose count means "how many people you can see in that group" from the very same set, and paging whose page, page size and total are all echoed by the server - the client never downloads every member and filters locally. Opening a row goes through the authorized single lookup `.../members/{member_id}` rather than expanding the list row on the device, so re-entering one after a permission change returns the same 1001, and whatever was on screen is cleared by the next authoritative request instead of an offline copy being treated as a grant. The four kinds of "nothing to show" each get their own sentence: nobody has joined, this mode lists nobody at all (paired with "your own profile still reads back"), the search or filter matched nothing inside what you can see, and this load failed - and the 1001 sentence never hints that there are people someone else can see. The activity status gets its own line, and a stopped or archived activity adds that directory reads are not gated by the lifecycle - so an ended activity still lists people and nobody mistakes "the activity is over" for "this directory could not be read." The own-profile section runs on its own path, so it keeps its content while the directory is closed and is never blanked along with it. The faction column tells three falsehoods apart: not assigned yet, an affiliation whose display values cannot be read, and an affiliation whose faction is disabled (from the new server-side `faction_available`, which describes that one column and is not folded into the activity status). Bio and avatar have no field in the contract, so the screen keeps a placeholder plus one sentence saying the field does not exist, with no upload or edit path; online status and online counts are likewise not guessed. Switching activities, signing out or changing servers rebuilds each card by id, every card carries its own request sequence, and a late response from an earlier filter, page or activity is dropped. No new dependency and no new machine code.
- The ordinary-account directory is browsable and maintainable now: the paginated directory filters by status (all／active／disabled／deleted), by source (all／standard／guest) and by a name keyword matched against the login and display name, and every page number and total is the server's echo. Opening a row first re-reads that one record from the server by its identifier, and only then does the edit form appear - though a row already in a terminal state re-opens read-only instead. This directory never lists administrators and never lists Root - anyone holding a server-level grant belongs to Root's administrator directory, and the two directories are disjoint. A session without administration rights gets "no permission" (2011) rather than an empty list, and an anonymous caller gets 2002. The form edits the display name only, and submits the current value it saw alongside it: a save against a stale screen is refused (2013) and overwrites nothing, and the interface offers "reload this record" instead of pressing save again. The login name is not edited here, and neither are credentials, roles or security state (any extra hidden field in the body is a 1004 from the server). A single record shows no activities, assets or messages: those modules do not exist, and the interface does not pad them with an empty list or a zero. A malformed identifier, a missing account, an account that is an administrator and an account still in the application book all answer the same 1001, so this endpoint is not a probe for whether someone is an administrator; the two terminal states are deliberately not among those answers - a deleted or retired row reads back fine, it simply cannot be changed.
- The activity page gained a third in-activity card: **tag definitions** (`GET`／`POST` on `/admin/activities/{id}/tags`, `PUT` on `.../tags/{tag_id}`). The card lists every definition of that activity, internal ones included, and each row labels it internal or public **in words** next to its icon and colour instead of letting a colour carry the meaning. Creating one sends four fields plus an optional sort value, and the create form deliberately has no public checkbox — a new tag is internal at birth, and the card says so. Editing sends the seven whitelisted values together with the seven `expected_*` they are based on, so a stale screen loses to 2013 with only a re-read offered, a name already used inside this activity answers the newly issued 2040 ("pick another name") and nothing is written, and a stopped activity answers 2033 while the list stays listed and readable. Publishing or un-publishing goes through a confirmation dialog that names the tag and reads out both halves of the consequence: the definition itself becomes readable to members of that activity, and it is not a role, grants no permission, does not make a single hidden player visible in the directory, and rewrites no existing reference. Availability is the other flag and the two stay independent — a published tag can still be disabled, and disabling keeps every reference it already had. There is no delete control on this card because that endpoint family has no DELETE: disabling is the reversible way to stop using a tag. And the card states plainly that attaching tags to players is not implemented — no member list, no count, not even a made-up zero.
- The player surface gained a read-only **published tag** card: `GET /player/activities/{id}/tags` lists only the definitions that activity's managers deliberately opened, and a row carries exactly id, name, description, icon and colour. The response has no availability field, no `public` field, no timestamps and no counts, so nothing on screen is padded with a placeholder; the card says in one line that this is a list of definitions and not anybody's tags (attaching a tag to a player does not exist yet), and that opening a tag up changes nothing about who the directory shows — that stays the four modes plus the per-row override. Not a member, Root, an id that was never public and an id that never existed all answer one indistinguishable 1001, and an anonymous request 2002. Nothing is cached on this client and the product has no push, so the claim stays exactly where the backend put it: after a manager un-publishes a tag, the next read simply stops listing it.
- Suspending and restoring an ordinary account's sign-in sits on the same single-record card, and the interface states the scope before anything is sent: what changes here is this account's ability to sign in to the whole server, not a player restriction inside one activity - a suspension refuses his future sign-ins and revokes every session he currently holds on every device. A confirmation dialog is mandatory before submitting; it names the target, reads out the blast radius and says this is not a deletion, and cancelling sends nothing. Which button appears is decided only by the state the server read back (active offers suspend, disabled offers restore, an unrecognized value gets one honest sentence instead of a guessed direction), and the value a change is based on is the state last read from the server - so acting on a stale screen is refused with 2014 and nothing at all happens, and the interface offers "reload this record" rather than pressing the button again. After a success the status, the suspension timestamp and "how many sessions this logged out" are all replaced with the server's response, and the directory is re-read; restoring brings back only the ability to sign in again - sessions revoked while the account was suspended do not come back, an unfinished first password change is still enforced by 2010, and a deleted account certainly cannot be restored this way. Guest accounts use the same controls, because this directory is defined as "holds no server-level grant". Muting inside an activity, transfer freezes and faction restrictions are not here, and nothing pretends they are.
- Resetting an ordinary account's credential sits on that same record card as a third whitelist: `PUT /admin/accounts/{account_id}/password`, whose body carries only `password` and deliberately no anchor value - the operator has no honest anchor such as "the current hash", so pressing that button again after an unclear outcome is not a retry but a second complete reset (revoking whatever sessions were minted in between and writing another audit row). The interface therefore never auto-resends. Delivery follows the scheme already approved on Root's side: the administrator hands the password over personally, the server generates nothing, echoes nothing and knows no default password; the field is masked, cleared before the request goes out, and the success sentence only states how many sessions were signed out plus "hand it over offline, first sign-in must change it". That string appears nowhere on screen afterwards and never reaches logs, audit rows, readable preferences or an auto-copied clipboard. A suspended account can still be reset - a reset is not an unsuspension, so the interface does not branch on status - and a reset leaves suspensions, deletion states and the outstanding first-change obligation exactly as they were. There is no account-level approval state today, so "pending approval" honestly means "still owes the first change": a reset writes "must change", never "need not". A guest account is out of this path's scope: he has no general password, and writing one would silently promote him into an ordinary account - that decision belongs to the guest-upgrade section on the same record card, and the server answers a reset attempted there with 2018. The interface therefore shows no reset button for guests and says that in one sentence. Not being allowed (2011), the target not being in this directory (1001) and a password that fails the server's rules (1004) each get their own sentence, and every number and label shown comes from the server's response rather than an optimistic guess.
- Upgrading a guest in place is the fourth whitelist on that same record card, and it only appears when the server-read source field says the target is a guest. `PUT /admin/accounts/{account_id}/upgrade` carries exactly two fields - the new login name and the one-time password - and there is no box for an account type, a role, a status or a flag: the upgraded shape is always an ordinary account that still owes a first password change, decided by the endpoint rather than the request, so "promote him into an administrator" is not something this screen can even ask for. The card states the two separations before anything is sent: this is an in-place conversion that keeps the same account ID, the display name and every past record (it is not creating a new account and deleting the guest), and it is not linking him to another existing account - that second path still has no execution route, and what the card can offer is only the read-only pre-check below. The confirmation dialog names both the target and the new login name. Like the reset, the password field is masked and cleared before the request goes out, nothing is echoed back, and there is no auto-resend on an unclear outcome. The success sentence reads its revocation count from the server's response: every session held by the old guest credential is signed out in the same transaction (the approved decision of this step, so a picked-up stale cookie never becomes a standard account by itself), and the only way back in is a real sign-in with the new credentials, immediately met by the first-change gate (2010). After success the card follows the server's returned record: the guest controls collapse, the reset section honestly appears, and the directory is re-read. A disabled guest gets no upgrade button - only the sentence saying to restore his sign-in first; already-upgraded or disabled targets get 2024, a taken login name gets 2012 with the guest row untouched, and the guest himself calling this endpoint gets 2011, because this administrator-only path exists precisely not to answer him.
- The guest binding pre-check is wired onto that same record card as a read-only preview: `POST /admin/accounts/{account_id}/bind-preflight` carries exactly one field - the target account ID - and evaluates one pair, "this guest times this target"; no reading lists bindable targets for a guest, and this screen is not a people search. It writes nothing: no account changes, no session revokes, no grants touched, no audit row; the result panel's first line states plainly that this is a pre-check and nothing has been linked. What comes back is a 200 preview rather than an error: when a binding is not possible, stable reason tokens name each cause - the same account on both sides, a source no longer a guest (upgraded or retired), a disabled source, a source carrying server-level grants (a defect direction), a guest as the target, a disabled target, and account references the pre-check has not been wired for (any such table blocks every binding until that module is registered; unregistered table names stay in the server log). The response also reports how many of the guest's sessions execution would sign out, which schema version the preview ran against, and a consent mode that is always target_self_initiated: when the binding path exists, only the target account's owner can start it from their own authenticated session - the administrator side will never hold a bind-on-someone's-behalf button, and that execution path does not exist today. A source or target outside the directory collapses to the same 1001 as the detail, the guest himself gets 2011, a missing or malformed target ID gets 1004 naming the field - and the pre-check itself publishes no machine code of its own.
- Issuing the binding ticket is that card's one write beside the read-only preview: `POST /admin/accounts/{account_id}/bind-ticket` again carries exactly one field - the target account ID - and the server re-runs the whole pre-check inside the issuing transaction, so a preview that passed is never a permanent grant to execute. What comes back is a 22-character plaintext that appears once, on that screen: it is pinned to this source, this target, this plan and the schema version the plan was checked against, it expires after a fixed 15 minutes, and spending it twice is impossible by construction - "repeated requests, switching target and replay must not change another account" is a structural guarantee here, not a promise. The plaintext is never cached locally and never reaches a log, an audit row, a preference or an auto-copied clipboard, while the audit does record the issuance itself (who approved which pair, when) as the first immutable trace of this migration. Pressing it always opens a confirmation that names the target and says out loud this is not the binding: this action retires nobody, logs nobody out, appends no history, and the administrator side will never hold a button that finishes somebody else's binding. If reality moved since the preview - an account-reference table appeared that this check was never wired for, either side's identity or sign-in ability changed, or the schema version advanced - the server answers the new machine code 2026 with its reason tokens and writes not a single byte; 2026's sentence says the disposition is to pre-check again and get a fresh ticket, never to press this button a second time. 1004 keeps naming the field, 1001 and 2011 keep their own sentences, and cancelling sends no request at all.
- The target account's owner then carries the binding out from the signed-in card, and that entry exists only for an ordinary account which is neither Root nor a server administrator and does not owe a first password change: pasting the ticket first runs a read-back of exactly this pair - which guest this authorizes, that the target is yourself, the five effects and the expiry - and only a second, separately confirmed action spends it. What the server then does, in one transaction, is revoke every session that guest held, move the guest account into a new terminal state (retired - neither disabled nor deleted, so his login name stays occupied and nobody can sign in with that identity again), keep his identity and every past record resolvable instead of rewriting history into "it was always the target account", and start attributing new activity to the target. Nothing is copied or merged behind anyone's back: the target keeps his own password, grants, status and assets, no balance or ledger entry moves, and the target's own ability to sign in is untouched - a spent ticket never becomes a token that logs in as somebody else. A ticket already spent, already expired, or not the one pinned to this pair answers one uniform sentence (machine code 2025) which deliberately does not say which of those it was, so this entry is not a searchlight for other people's tickets. Where the binding would touch a local business reference this build has not been wired for, the server refuses it (2026) and says so - data is never deleted to make a check pass. If execution fails, the previously usable relations are exactly as they were and the screen says failed; if the response is lost after the server committed, the screen says "result to be confirmed" and does not re-send, while a read-only ledger (`GET /auth/guest-bindings`) lists the bindings already completed into this account and settles what actually happened. Failed, completed and to-be-confirmed therefore stay three different statements, and an unclear outcome is never clicked into a second migration.
- Soft-deleting an ordinary account or a guest is the last write path on that same detail card, and the interface states the scope first: what changes here is this account's ability to sign in on the whole server, not a player restriction inside one activity - that sentence sits above the button, so it is read before anything is pressed rather than being an appendix inside the dialog. `DELETE /admin/accounts/{account_id}` carries no request body at all: `{}` is accepted, and any single extra field - a reason text or an expected value included - is refused with 1004. There is deliberately no expected-value field, because "the current deletion moment" is not something the operator can hold as an honest anchor; the authority is the state-machine guard, so a second delete writes nothing and is refused instead of reporting a fresh success. The confirmation dialog names the target (login name, source type and the status read back from the server), states the three things that happen (new sign-ins are refused, every session he holds right now is signed out, and the display name becomes the server's anonymised placeholder) and the two that do not (this is not disabling - a deleted account has no restore path - and the login name stays occupied, so nobody else can take it), and says why the account row is kept on purpose: existing audits and history must still resolve to the same person. Cancelling sends nothing, and there is no "I understand" checkbox - that dialog is itself the last handle. After success the card leaves edit mode: the name field and every write button disappear, leaving only the server's post-delete truth, a read-only banner carrying the deletion moment, and a revoked-session count that comes from the response rather than from a guess. Both terminal states render read-only without exception: on a `deleted` or `retired` row the edit form, the disable and restore buttons, the password reset, the guest upgrade and the bind pre-check and ticket issue are all gone, and the card shows only what the server says. A deleted target answers 2027 and a guest already bound into another account answers 2028 (before this step the card used to offer a retired guest a rename form, and that write was refused server-side); for the retired one the sentence to read is the binding trace - he is not gone, he continues as the account he was bound into. Each state offers exactly one way out, re-reading this record, never pressing again. When an outcome is unknown the delete is never resent: whether it happened is answered by re-reading the directory and the record. This directory cannot list grant-holders or the configured Root by definition, so an ordinary administrator deletes neither a peer administrator nor Root - those identifiers, malformed ones and ghost ids all converge on the same 1001, and the endpoint is not an identifier probe. Physical purging, bulk deletion, self-service account cancellation and any automatic cleanup of stale guests do not exist, and the interface does not pretend otherwise.
- Registration applications have their own screen on the administrator console. `GET /admin/registrations` lists the ones still waiting and the ones already declined: each row shows the login name, display name, status, submission time and - once a decision exists - the decision time, and nothing else. That is the whole set of facts reviewing needs; there is no credential, no session material and no role column, and the ordinary-account directory stays a separate book with its own scope rules. The two buttons appear only when the server's own status says `pending`. A declined row gets one honest sentence instead, because a decision is one-way here: nothing reopens it, and that login name stays taken. Neither button has a reason box next to it - internal notes and public reasons are stored nowhere, and the screen offers no field whose contents would be silently dropped. Confirming names the target and says both what lands (an ordinary account able to sign in with the password it chose, holding no server role) and what does not (no session is issued for that person, no suspension is lifted, nothing is renamed or deleted). The success sentence comes from the PUT response - which decision landed and whose application it was - and then the list is re-read instead of the row being edited locally, because an approved person is no longer in this book. 2021 means the application has already been decided: the screen offers only a reload and never re-sends a decision on an unclear outcome. 1001 means the target is not in this list at all, and 2011 means this session may not decide about anybody - three different dispositions, each with its own sentence. Nothing here announces the result: this server has no notification module, so the applicant learns the outcome only by proving their own credentials again on the status screen.

- The rest of the Root management modules are still under development: the signed-in home shows only the true identity and entries that actually work today, and nothing is padded with sample data. Identity lines follow the `roles` the server returns, so an administrator sees "server administrator" and an account without grants does not; a signed-in administrator who opens the same creation form is told plainly that they lack permission (code 2011), and signing in again does not change that. Session credentials are kept by the browser's HttpOnly cookie on web, and by system-level secure storage on native clients — never in plain local files. On web that cookie is marked Secure only when the page is actually served over HTTPS; on a plain-HTTP LAN deployment the browser's protection comes from SameSite plus the server's origin check, so using HTTPS means putting your own TLS-terminating reverse proxy in front of the server.

## Server address

The server entry page lets you type the address of the server you want to use and keep it on this device, so switching between test servers no longer needs a rebuild. Only a complete `http://` or `https://` address that carries no user name or password is accepted, and an address is saved only after it answers. A wrong format is reported with the specific reason — for example "The address must start with http:// or https://" — and no request is sent at all; an address with a valid format that does not respond is not saved, and the page says why instead of pretending otherwise. The address in use and the address saved on this device are listed separately, together with where the current one came from; a debug build keeps the build parameter `--dart-define=ER_SERVER_BASE_URL` in priority and states on screen that a locally saved address is not yet in effect. Your entry is stored on your own device only.

## When something goes wrong

If part of the app cannot be displayed, the interface switches to a safe notice page: it says where the problem happened (drawing the interface, a background task, or talking to the server), gives a diagnostic code you can match against this device's log, and includes the server request ID when the failure involves a request. A single action, "Return to a working page", takes you back to an usable interface. The notice page never shows the raw error text, a stack trace, or the server address, and nothing is sent anywhere — problems are recorded on your own device only.

One honest caveat: the section that just failed may stay blank for a while after you return, until the interface rebuilds. If the same problem keeps coming back, the notice page will tell you to reload the app.

## Building from source

The per-platform icons and launch screens are generated, not committed: they are derived from the four source images in `assets/icons/`. On a fresh clone, run

    python tools/icons/generate_icons.py

before building — Android, iOS, macOS and Windows builds fail while their icon resources are missing, and a web build would ship without icons. `python tools/icons/generate_icons.py --check` reports the current state without writing anything; see `tools/icons/README.md`.
